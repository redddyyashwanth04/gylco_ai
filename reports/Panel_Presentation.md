# Carepath: AI-Powered Clinical Decision Support for Type 2 Diabetes
### Panel Presentation — Technical & Non-Technical Brief

---

## 1. The Problem — Why This Exists

**480 million people** globally live with Type 2 Diabetes. The clinical burden is not the diagnosis — it is managing what comes next: hypertension, nephropathy, cardiovascular events, and glycaemic deterioration. These complications are largely predictable from routine lab values, yet the average GP appointment is 10–15 minutes. Clinicians do not have time to mentally integrate 8–10 biomarkers, compare trends across visits, and generate a structured follow-up plan for every patient.

Existing tools fall into two categories:

| Category | Example | Problem |
|---|---|---|
| Static risk calculators | Framingham, UKPDS | Single-output, no driver explanation, no trend tracking |
| EHR-integrated AI | Epic Sepsis Model, Optum | Black-box, institution-locked, $100K+ deployment |
| Research dashboards | Custom Jupyter notebooks | Not clinician-facing, not interactive |

**The gap:** there is no lightweight, explainable, offline-capable clinical decision support tool that a clinician can run from their own machine, see *why* a risk is elevated, and track a patient's trajectory over time.

Carepath is built to fill exactly that gap.

---

## 2. What Carepath Does — One Paragraph

Carepath is a clinician-facing prototype that takes a patient's routine measurements (HbA1c, glucose, blood pressure, BMI, lipids) and returns three things: an estimated risk of hypertension, nephropathy, and cardiovascular complications; a ranked explanation of which factors are driving each risk estimate; and a forecast of the patient's next glucose reading. Every result is stored in a local audit trail. Every explanation is generated without sending patient data to any external server. The system runs entirely on the clinician's own machine.

## 3. The Full User Journey

### Step 1 — Login
The clinician navigates to `http://127.0.0.1:5001`. A login screen validates credentials (`dr.smith / clinic123`). Authentication is session-based via `sessionStorage`. The application does not transmit any data outside the local machine.

**What the panel sees:** a professional dark-sidebar clinical workspace UI — not a research notebook, not a generic dashboard.

### Step 2 — Overview
The landing page shows four live tiles:
- **Track A model** active: `nhanes_random_forest` — Registry v34 · AUC 0.818
- **Track B model** active: `LSTM v4 + Ridge blend` — Registry v33 · MAE 45.4 mg/dL
- **Patients tracked** — pulled live from SQLite
- **Predictions logged** — audit count from the prediction log table

The tiles are populated by a single `GET /api/health` call on startup. If the Python server is offline, every tile degrades gracefully with an "offline" label — the UI never shows a blank or a crash.

### Step 3 — Current Assessment (Track A)
The clinician fills in:
- **Required:** Age, HbA1c, Fasting glucose
- **Optional:** BMI, Blood pressure, LDL, HDL, sex, smoking status, sedentary time, income-to-poverty ratio

They click **Review visit**. Within ~200ms the server returns:

```
Hypertension risk:   74%
Nephropathy risk:    61%
Cardiovascular risk: 58%
```

Simultaneously (non-blocking, fires in parallel) the **Top Drivers** SHAP panel renders:
- Orange bars = features raising the risk
- Green bars = features lowering it
- Fields not entered are flagged *"typical value assumed"* so the clinician knows what was imputed

A **plain-English narrative** appears beneath the chart, generated by Llama 3.3 70B (Groq API) from the SHAP values alone — the LLM is forbidden from adding any clinical advice not grounded in the numbers. If Groq is offline, a deterministic template generates the narrative automatically.

**Trend arrows** appear if the patient has a prior visit saved — the system computes the delta and shows ↑ or ↓ against the previous risk snapshot.

The clinician can add a **visit note**, then click **Save visit to patient record**. The measurements, risk snapshot, model version ID, and note are written to a local SQLite database.

### Step 4 — Progression Forecast (Track B)
The clinician selects a tracked patient from the dropdown. Their historical glucose readings are plotted on a canvas chart. Clicking **Forecast next reading** sends the last 7 readings to the LSTM v4 model, which returns:

- A forecasted next glucose value in mg/dL
- The change from the last observed reading
- A ± error bar (leave-one-patient-out MAE = 45.4 mg/dL)
- The model name: `LSTM v4 + Ridge blend`

The forecast point is plotted in orange with the error bar drawn on the chart.

### Step 5 — Patient History
A searchable, sortable table of all saved visits. Each row shows: patient ID, visit date, HbA1c, glucose, BMI, blood pressure, and the risk triple (H · N · C as percentages). Clicking a patient ID navigates directly to their trajectory view.

### Step 6 — Model Transparency
A live registry table showing every model version ever trained, with: training date, row counts, AUC/F1/MAE, active status, and the full notes string. Updated automatically every training run. No manual documentation required.

## 4. Technical Architecture

```
┌─────────────────────────────────────────────────────────────────┐
│                     Browser (localhost:5001)                     │
│  login.html → index.html (SPA)                                  │
│  app.js  ─── 6 API endpoints ──► api_server.py                 │
└──────────────────────────┬──────────────────────────────────────┘
                           │ HTTP (loopback only)
┌──────────────────────────▼──────────────────────────────────────┐
│                      api_server.py                               │
│  POST /api/predict   → predict.py  → nhanes_rf_*.pkl            │
│  POST /api/explain   → explain.py  → SHAP + Groq/template       │
│  POST /api/forecast  → train_lstm.predict_from_checkpoint()      │
│                          → mimic_lstm_forecaster.pt              │
│  GET  /api/health    → checks artifacts, reads registry          │
│  GET/POST /api/visits → db.py → app_state.db (SQLite)           │
│  GET  /api/models    → db.py → model_registry table             │
└──────────────────────────┬──────────────────────────────────────┘
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
   predict.py         train_lstm.py       db.py
   3× per-label RF    GlucoseLSTM v4      SQLite
   _MODEL_CACHE        _INFER_CACHE        4 tables
   medians cached      mtime-based
```

**Key design decisions:**
- **Loopback-only** — the server binds to `127.0.0.1`. No data ever leaves the machine.
- **Lazy loading with mtime caching** — models reload automatically when retrained, without restarting the server.
- **Medians cached at model load** — the training CSV is read once, not on every prediction request.
- **Inference decoupled from training** — `predict_from_checkpoint()` in `train_lstm.py` is the single source of truth for Track B inference.

## 5. Machine Learning Details

### Track A — NHANES Complication Risk

| | Value |
|---|---|
| Dataset | NHANES population survey (CDC) |
| Training rows | 6,522 |
| Test rows | 1,631 |
| Features | 36 (raw + engineered: lipid ratios, prediabetes flag, BP flag) |
| Active model | Random Forest (300 trees, class-balanced) |
| Hypertension AUC | 0.822 |
| Nephropathy AUC | 0.791 |
| Cardiovascular AUC | 0.841 |
| **Mean AUC** | **0.818** |
| Comparison: Logistic Regression AUC | 0.817 |
| Comparison: Gradient Boosting AUC | 0.813 |

Three separate single-output Random Forest models are trained per label (for stable SHAP) alongside the multi-output wrapper (for comparison). The winner is determined by mean AUC on the held-out 20%.

**Why Random Forest beats Gradient Boosting here:** HistGradientBoosting achieves higher F1 (0.521 vs 0.459) by predicting the majority class more aggressively on imbalanced labels. RF wins on AUC (0.818 vs 0.813) which better reflects discrimination ability for a decision-support tool where calibration matters more than binary accuracy.

### Track B — MIMIC-IV Glucose Forecast

| | Value |
|---|---|
| Dataset | MIMIC-IV Demo (ICU, de-identified) |
| Real patients | 25 |
| Real windows (gap < 24h) | 661 |
| Total windows (augmented) | 3,305 |
| Architecture | 2-layer LSTM + horizon bucket embedding + patient context vector |
| Hidden size | 64 |
| Dropout | 0.3 |
| Seeds (ensemble) | 3 |
| Blend alpha (LSTM weight) | 0.85 |
| Synthetic pretraining | Yes (1,000 AR(1) patients, 185K windows) |
| Naive baseline MAE | 54.5 mg/dL |
| Ridge MAE | 46.3 mg/dL |
| **LSTM v4 + Ridge blend MAE** | **45.4 mg/dL** |
| Improvement over naive | 9.1 mg/dL (17%) |
| Validation method | Leave-one-patient-out CV |

**Four innovations stacked in v4:**
1. **Gap filter** — only train/evaluate on windows where the next reading is < 24h ahead. Removes unlearnable multi-day noise.
2. **Horizon bucket embedding** — time-to-next-reading is bucketed into 4 classes; a learned 4-dim embedding is concatenated to the LSTM head. Lets the model adopt different strategies per horizon class.
3. **Patient context vector** — per-patient mean, std, trend slope, and last-reading z-score fed into the head. Gives a patient-level prior without a full embedding table.
4. **Synthetic pretraining** — 1,000 AR(1) glucose trajectories pretrain the LSTM before fine-tuning on real data. Reduces overfitting on 25 patients.

### Explainability (SHAP)

| | Value |
|---|---|
| Method | TreeExplainer (RF), Explainer fallback (HistGBT) |
| Features shown | Top 5 per label |
| Correlated deduplication | Yes — TC/HDL ratio replaces raw total cholesterol |
| LLM narrative | Llama 3.3 70B via Groq (grounded strictly to SHAP values) |
| Offline fallback | Deterministic template (always available) |
| Top-3 stability (±5% noise, 20 trials) | **62%** mean (nephropathy 95%, hypertension 25%) |

## 6. Data Engineering

### NHANES Pipeline
1. Raw `.XPT` survey files → `merge_nhanes_core.py` → merged CSV
2. Feature engineering: lipid ratios, prediabetes flag, lab hypertension flag
3. Leakage-safe: 8 leakage columns explicitly dropped before training
4. Stratified 80/20 split, fixed seed for reproducibility

### MIMIC-IV Pipeline
1. Raw `.csv.gz` demo files → `build_mimic_trajectories.py` → long-format CSV (1,212 glucose readings, 35 patients)
2. Window slicing (stride=1, window=8) → 661 short-gap real windows
3. Jitter augmentation (±2% noise, 4 copies) → 3,305 total windows
4. Synthetic pretraining: `generate_synthetic_mimic.py` → 1,000 bootstrap-perturbed AR(1) patients

### Key data integrity rules:
- All augmented windows from one patient stay in the same LOPO fold (no leakage)
- Every result reports real patient count separately from augmented count
- Gap filter (< 24h) applied consistently to train, validation, and test

## 7. Persistence & Audit Trail

Every prediction is logged to SQLite with: timestamp, model name, version ID, patient ID, and the full prediction dict. The `model_registry` table records every training run with AUC, F1, MAE, and notes. Training run reports are automatically written to `reports/training_runs/` as timestamped JSON + Markdown on every `train_all.py` run.

## 8. Advantages

**For clinicians:**
- Works offline — no internet required, no data leaves the machine
- Explains every estimate — SHAP shows exactly which measurements drove the risk
- Tracks trends — delta vs previous visit with directional arrows
- Non-prescriptive — outputs are "points for review", not treatment orders

**Technical:**
- Full SHAP explainability on every prediction
- Automatic model versioning and promotion with validation gating
- mtime-based artifact caching — no server restart needed after retraining
- Synthetic pretraining extends effective training data 5× without leaking real patient information
- Inference logic in one place (`predict_from_checkpoint`) — server just calls it

**Architectural:**
- Loopback-only binding — cannot be accidentally exposed to a network
- Graceful offline degradation: LLM → template, LSTM → Ridge fallback
- Complete audit trail: every prediction logged with model version ID

## 9. Disadvantages & Honest Gaps

| Gap | Impact | Mitigation |
|---|---|---|
| NHANES labels are self-reported | Survey bias affects Track A targets | Documented; AUC still 0.818 |
| Track B: only 25 ICU patients | High OOD risk for outpatient glucose | Error bar shown on every forecast |
| SHAP stability 62% (hypertension 25%) | Top-3 ranking noise-sensitive for tied features | Per-label models trained; acknowledged in paper |
| Login is client-side only | sessionStorage can be bypassed | Appropriate for local research prototype |
| No insulin/medication data | MAE floor ~45 mg/dL vs potential 20–25 | Full MIMIC-IV requires credentialed PhysioNet access |
| Retraining not yet wired to UI | Clinician cannot trigger from browser | Pipeline designed and validated |
| Synthetic AR(1) trajectories are smooth | Can't model medication spikes | GAN not viable at N=25 |

## 11. What Makes This Research-Grade

1. **LOPO-CV** — with only 25 patients, a single train/test split is statistically invalid. LOPO-CV is implemented correctly with augmentation integrity preserved.

2. **Synthetic pretraining with honest reporting** — every result table reports `real_patients=25, synthetic_patients=1000` separately. Enforced through the `TrainingRun` metrics logger.

3. **SHAP stability measurement** — the paper reports 62% top-3 stability with the exact protocol (±5% Gaussian noise, 20 trials, mean across three labels). Most clinical AI papers omit this test entirely.

4. **Validation-gated model promotion** — the retrain pipeline requires a candidate model not to regress more than 0.01 AUC before promotion.

5. **Gap filter justified from data** — median gap in raw data is 20.7h but p90 is 346h. Training on multi-day gaps was adding ~4–5 mg/dL of unlearnable noise to the MAE. The filter is data-driven, not arbitrary.
